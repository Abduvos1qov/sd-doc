# Contributing to sd-docs

This page is the entry point for anyone adding or editing content in sd-docs. If you're a translator, jump to [Translating →](./translating). If you're adding screenshots, jump to [Screenshot pipeline →](./screenshot-pipeline). For voice / terminology / MDX rules, see [Style guide →](./style-guide).

## What sd-docs is

`sd-docs` is the developer-and-client documentation for the SalesDoctor ecosystem (sd-main, sd-cs, sd-billing). It's a [Docusaurus 3.x](https://docusaurus.io) site with two doc collections:

| Collection | URL prefix | Audience |
|-----------|-----------|----------|
| `docs/` | `/docs/*` | Backend engineers, QA, PMs, ops |
| `guide/` | `/guide/*` | Dealer admins onboarding to the product (no internals) |

Plus three locales — English, Russian, Uzbek (Latin) — under `i18n/`.

## Local setup

```bash
git clone <repo>
cd sd-docs
npm install
npm run start          # http://localhost:3000 with hot reload
```

To build the production output and serve it locally:

```bash
npm run build          # all 3 locales, ~3 minutes
npm run serve          # serves the build/ at http://localhost:3000
```

Both `start` and `serve` default to port 3000. If you also run sd-main on `localhost:8080`, the two don't conflict.

## Adding a new doc page

### Pick the right collection

- **`/docs/*`** for developer content (architecture, modules, API, schema, RBAC, settings). Sidebar is `sidebars.js`.
- **`/guide/*`** for client-facing onboarding (step-by-step screenshots, no internals). Sidebar is `sidebars-guide.js`.

### Create the file

```
docs/<section>/<your-page>.md     # for developer docs
guide/<section>/<your-page>.md    # for client guide
```

Naming rules:
- Use **kebab-case** (`my-new-page.md`, not `myNewPage.md`)
- Add a `.md` extension (not `.mdx` unless you need JSX)
- Avoid spaces, accents, or punctuation in filenames

### Frontmatter

Every page starts with YAML frontmatter:

```yaml
---
sidebar_position: 10
title: Your page title
audience: Backend engineers, QA
summary: One-sentence summary used by the RAG indexer.
topics: [tag1, tag2, tag3]
---
```

| Key | Required | Purpose |
|-----|----------|---------|
| `sidebar_position` | yes | Order in the sidebar (lower = earlier) |
| `title` | yes | Page title (translated per locale) |
| `audience` | recommended | Who this page is for |
| `summary` | recommended | One-line description (RAG-indexed) |
| `topics` | recommended | Tag array (RAG-indexed) |
| `slug` | optional | Override the default URL slug |

### Sidebar registration

Two ways:

1. **Autogenerated** (default for some sections) — just create the file and it appears, sorted by `sidebar_position`.
2. **Explicit** — open `sidebars.js` (or `sidebars-guide.js`) and add the page ID to the appropriate category.

If your page doesn't appear after `npm run start`, run `Ctrl+C` and restart — Docusaurus picks up new files at restart.

### i18n mirroring (critical)

Every new file in `docs/` or `guide/` MUST have a matching file in **both** `i18n/ru/` and `i18n/uz/`. If the translations don't exist yet, copy the EN content verbatim into the i18n paths — this keeps the multi-locale build green until translators arrive.

Paths:

```
docs/<section>/<page>.md
  → i18n/ru/docusaurus-plugin-content-docs/current/<section>/<page>.md
  → i18n/uz/docusaurus-plugin-content-docs/current/<section>/<page>.md

guide/<section>/<page>.md
  → i18n/ru/docusaurus-plugin-content-docs-guide/current/<section>/<page>.md
  → i18n/uz/docusaurus-plugin-content-docs-guide/current/<section>/<page>.md
```

**Build fails on the first locale** that's missing a file referenced in the sidebar. Catch this locally before opening a PR.

## Editing an existing page

1. Edit the EN version under `docs/` or `guide/`.
2. **Decide if the change requires re-translation.** Trivial fixes (typos, link updates) can be applied to all 3 locales identically. Substantive content changes need a real translation pass — see [Translating →](./translating).
3. If a screenshot reference changes, update all 3 locales.
4. Run `npm run build` to verify all 3 locales still compile.

## Adding screenshots

Full pipeline in [Screenshot pipeline →](./screenshot-pipeline). Short version:

1. Capture from `localhost:8080` (the demo tenant) using Playwright or a screenshot tool.
2. Save to `static/screens/guide/<NN>-<surface>.png` (e.g. `66-new-feature.png`).
3. Run `python3 scripts/optimize-guide-images.py` to generate a WebP variant.
4. Reference the `.webp` in your markdown.
5. (Optional) Define callouts in `static/data/callouts-guide/<NN>-<surface>.json` and run `python3 scripts/annotate-guide-screenshots.py` to overlay numbered circles.

## Pre-flight before opening a PR

```bash
# 1. Lint Mermaid diagrams (if any)
bash scripts/lint-mermaid.sh

# 2. Build all 3 locales
rm -rf .docusaurus build
npm run build

# 3. Spot-check the rendered output
npm run serve
# open http://localhost:3000/docs/<your-page>
# open http://localhost:3000/guide/<your-page>
```

Common build failures and what they mean:

| Error message | Fix |
|---------------|-----|
| `Markdown link with URL '...md' couldn't be resolved` | A relative link points at a non-existent file. Check the path. |
| `Markdown image with URL '/screens/...' couldn't be resolved` | The image file isn't in `static/screens/`. |
| `Unexpected character '0' (U+0030) before name` | MDX is parsing bare `<N` or `<word>` as a JSX tag. Wrap in backticks. See [Style guide →](./style-guide). |
| `Unexpected end of file in expression, expected a corresponding closing brace for '{'` | Bare `{...}` outside backticks confused MDX. Wrap in backticks or write as prose. |

## PR checklist

Before requesting review:

- [ ] All 3 locales (en/ru/uz) have the file
- [ ] `npm run build` passes locally
- [ ] Screenshots (if any) are `.webp` and reference paths exist
- [ ] No bare `<N`, `<word>`, or `{x}` outside backticks (see [Style guide](./style-guide))
- [ ] Cross-links to related pages (a page in isolation is harder to find)
- [ ] Frontmatter `summary` reads cleanly out of context (it shows up in the RAG)
