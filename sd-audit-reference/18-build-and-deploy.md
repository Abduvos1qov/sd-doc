## Codegen — `build_runner` and the manual edit

The project uses `flutter pub run build_runner build` (not the newer
`dart run build_runner`) for ObjectBox bindings. Output:

- `lib/db/objectbox.g.dart` — generated by `objectbox_generator`
- `lib/db/objectbox-model.json` — schema snapshot the generator uses
  to track entity-ID / property-ID renames across runs

**The manual edit** (documented in the project root `README.md`):

After every codegen, open `lib/db/objectbox.g.dart` and find any
generated line that looks like:

```dart
relInfo: obx_int.RelInfo<EditedClientBox>.toMany(...),
toMany: () => obx.ToMany<AgentEditedVisitDaysDataBox>?  // <-- nullable
```

Remove the trailing `?` so the type becomes `obx.ToMany<...>` (the
codebase expects non-null). Do this for **every** occurrence
involving `AgentEditedVisitDaysDataBox`.

Why: the generator can't tell that the codebase requires a
non-nullable `ToMany` for these specific relations; the entity field
itself is declared without the `?`, but a generator quirk emits a
nullable type in the relation metadata. A different relationship
definition style might be the real fix; nobody's pushed that change
yet.

**Failure mode:** without the edit you'll see compile errors of the
shape `The argument type 'ToMany<...>?' can't be assigned to the
parameter type 'ToMany<...>'`. Re-run codegen, re-apply the edit.

A safer long-term fix:

- Define the relations using explicit `Backlink`/relationships in
  `lib/db/relationships/*.dart` (which already exists for several
  relations).
- Or write a small post-codegen script (e.g. a Makefile target) that
  applies `sed` to the generated file.

## iOS

CocoaPods must be installed (`gem install cocoapods` or `brew install
cocoapods`). `cd ios && pod install` rewrites `Podfile.lock` to match
the current pubspec.

If you see `error: SwiftFlutterMap` style errors at build time, the
pods cache may be stale: `cd ios && rm -rf Pods Podfile.lock && pod
install`.

The minimum iOS deployment target is set in `ios/Podfile`. Flutter
default is 12.0 — some plugins (Firebase, geolocator) may push that
higher.

## Android

`android/app/build.gradle.kts` (or `.gradle` if older) sets `minSdk`,
`compileSdk`, `targetSdk`. Background-location requires
`ACCESS_BACKGROUND_LOCATION` and a `foregroundServiceType=location`
declaration in the manifest.

Release builds need a signed keystore. Configuration goes in
`android/key.properties` (not checked in).

## Firebase

`firebase_options.dart` is generated by `flutterfire configure`. If
you switch Firebase projects (e.g. dev vs prod):

```bash
flutterfire configure --project=your-project-id
```

This rewrites `firebase_options.dart`. Both Android `google-services.json`
and iOS `GoogleService-Info.plist` get regenerated — commit them with
care if you have separate dev/prod files.

## Version & build numbers

`pubspec.yaml`:

```yaml
name: sdaudit
version: 3.1.2+25
```

The string before `+` is the semantic version; after is the build
number. Both get baked into the APK / IPA. Bump the build number on
every store upload (Play Console + App Store Connect reject
duplicate builds).

The `AppVersionManager` (`/app/audit` endpoint) compares the running
build's `version` string to the server-stored "latest". Force-update
flags trip when the difference is significant.

```bash

flutter pub get
flutter pub run build_runner build --delete-conflicting-outputs
# (apply the manual ToMany fix to objectbox.g.dart)
cd ios && pod install && cd ..   # macOS only
flutter run                       # device or simulator
```

## CI considerations

There's no CI config in the repo at doc time. If you add one:

- Cache `~/.pub-cache` and `~/.gradle/caches`.
- Run `flutter analyze` and `flutter test` per PR.
- Build the APK / IPA on tagged commits.
- **Re-running `build_runner` will undo the manual edit** — the CI
  job either needs to apply that sed automatically, or codegen
  output should be committed (current approach).
